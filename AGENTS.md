## Project Conventions

### Scope

This is **Easy Ponto**, the timekeeping system of Supermercado Baratão. It reads the company, the employees and the punch records from the time clock (a Control iD iDClass, called the device in the code, through its HTTPS API). The store uses Secullum today, so importing its **Cartão Ponto** report (`.xls`, `.xlsx` or `.csv`) is a migration aid, not part of the regular flow: it brings over what the device doesn't have (department, position, admission date, payroll number, schedule) and the punches added by hand in Secullum. The stack: Postgres through **Drizzle ORM** (`drizzle-orm` and `drizzle-kit`, 1.0 release candidates, with the `pg` driver), Server Components and Server Actions (there is no public API), and **shadcn/ui** on Base UI for the interface.

Easy Ponto is multi-company: each account belongs to one or more companies and sees only the data of the active one. Authentication uses **better-auth** (`src/infra/auth.ts`) with the Drizzle adapter and the `organization` plugin, where the company is the organization. Server code reads the session through `src/entry/session.ts`: `requireCompany` (the private pages) returns the signed-in account, the active company and its device credentials, and redirects to `/entrar` otherwise. Server Actions take the company and the device credentials from there, never from the client, and the device password is never passed to a client component (#54). Each member has a role in the company (`members.role`, constants in `src/models/account/utils.ts`): `owner` and `admin` edit everything, `viewer` sees every private page but edits nothing, and `employee` only reaches `/meu-ponto`; an unknown role edits nothing (`canEdit`). Every Server Action of a private page and every page that only edits (`/configuracoes`, `/membros`) call `requireEditor` instead of `requireCompany`. It sends the viewer to `/registros-de-ponto`, so the server refuses the edit whatever the UI shows. A page's `data.ts` returns the `canEdit` of `requireCompany` and the page passes it down, so the editing controls (and the instructions that lead to them, as in the empty states) aren't even rendered for the viewer. The private layout also passes it to `PermissionsProvider` (`src/app/components/providers/`) for the client components it reaches without props (`useCanEdit()`), such as the sidebar, where an item that only edits takes `editOnly`. The owner and the admins manage the other members in `/membros` (`memberModel`, rules in `src/models/member/utils.ts`), which leaves the employees out: they are managed in `/funcionarios`. There is no email service, so the editor adds a member with a temporary password that must be changed on the first access, and an email that already has an account (from another company) only gets the membership, keeping its name and password. The admin adds, changes and removes only viewers; the owner also manages the admins and transfers the ownership, becoming an admin. The owner role is never assigned, removed or changed otherwise, so the company always has exactly one owner, and no one changes their own role or removes themselves. Removing a member deletes only the membership and the sessions open in that company, since the account may belong to other companies.

### Package manager

- Use **pnpm** only (not npm/yarn).
- Versions are pinned exact (no `^`/`~`) for `dependencies` and `devDependencies` in `package.json`. Install new deps with `pnpm add -E <pkg>` (or `pnpm add -D -E <pkg>`) — never hand-edit version strings.
- `-E` only takes effect when no version is given. `pnpm add -E <pkg>@<version>` (or `@latest`) and packages already in `package.json` still get a `^`. In those cases, remove the carets right after (`sed -i -E 's/"\^([0-9])/"\1/' package.json`) and run `pnpm install`.
- The exact-version rule does not apply to MCP servers (`.mcp.json`) or `package.json` scripts, which may use `@latest` (e.g. `pnpm dlx shadcn@latest`, `pnpm dlx @playwright/mcp@latest`). They must still run through pnpm, never `npx`.
- `minimumReleaseAge` in `pnpm-workspace.yaml` (7 days, in minutes) keeps pnpm from resolving a version published less than a week ago.
- Node version is pinned in `.nvmrc` (`lts/krypton`) and in `engines.node` (`24.x`). Keep both on the same major.
- `xlsx` comes from the SheetJS CDN (`https://cdn.sheetjs.com/...`), since the npm package is no longer updated.
- `@/*` resolves to `src/*` (`tsconfig.json`).

### Project structure

- `src/app` holds frontend-exclusive content only. Server code (the layers below) and `src/tests` live directly under `src`, as siblings of `app`.
- Routes are grouped under `src/app/(pages)`, with nested groups by audience: `(public)` (landing page and `/status`), `(auth)` (`/entrar`, `/configuracao-inicial` and `/trocar-senha`), `(employee)` (`/meu-ponto`, the employee's page, inside a layout with the header) and `(private)` (the company pages, inside the sidebar layout, whose `layout.tsx` calls `requireCompany`). The `error.tsx` of `(pages)`, `(private)` and `(employee)` show a rendering error inside the layout of each area, with the `digest` that support can match to the server log, and `(pages)/not-found.tsx` is the 404 of the whole app: the root layout lives in the `(pages)` group, so an unmatched URL only reaches it through the `[...unknown]` route, which calls `notFound()`. Both render `blocks/page-message.tsx`. Shared client hooks live in `src/app/hooks` (`use-<name>.ts`), and the UI copy and helpers shared across route trees (e.g. the status and weekday labels) in `src/app/utils` (`<name>.ts`).
- `src/app/components` groups components by role: `ui/` for visual building blocks (shadcn ones under `ui/shadcn/`, other registries under their own folder, e.g. `ui/magic-ui/`, `ui/shadcn-io/`, and our own under `ui/custom/` and `ui/icons/`), `blocks/` for composed pieces reused across pages (e.g. `blocks/app-sidebar/`, `blocks/users-filter.tsx`, the name, position and status filter of `/funcionarios` and `/expedientes`, and `blocks/punch-records-table.tsx`, shared by `/registros-de-ponto` and `/meu-ponto`, and `blocks/report-import-form.tsx`, the report imports of `/configuracoes` and `/relatorio-de-horas`, with the source system select and the unknown codes dialog) and `providers/` for context providers without UI of their own.
- Server code is layered, and imports only flow down: `app` → `entry` → `models` → `repositories` → `infra`, with `constants` as a leaf every layer may import (it imports none of them). `no-restricted-imports` in `eslint.config.mjs` enforces the direction per folder, and, among `app`, `entry` and `models`, none may import the database client (`src/infra/database/client.ts`): queries go through `repositories`.
  - `src/entry/` adapts Server Actions to the models (`handleFormAction`) and holds the session (`session.ts`), the only place that calls `auth.api`. `requireCompany` redirects by throwing, so an action calls it before its `try`, and an action that redirects after a successful `handleFormAction` does it outside of it.
  - `src/models/<domain>/` holds the business rules of one domain: `model.ts` (exports `<domain>Model`), and, when needed, `schema.ts` (Zod schemas), `types.ts`, `errors.ts` and `utils.ts`. A domain with several internal helpers keeps them in `_utils/` (e.g. `src/models/synchronization/_utils/afd.ts`). `src/models/device/` talks to the time clock through adapters (see Time clock & synchronization).
  - `src/repositories/<domain>-repository.ts` exports `<domain>Repository` with the queries of one domain.
  - `src/infra/` holds the technical base: the database (`database/`), `dayjs`, the errors and the local services and scripts. `src/constants/` holds values shared across layers (e.g. the document lengths).
- Type aliases start with `T` (`TDeviceUser`, `TCompanyState`). The row types are in `src/infra/database/types.ts`, inferred from the schema (`User`, `Company`, ...), with `TInputData<T>` for a row without `id`/`createdAt`/`updatedAt`.
- There are no `index.ts` barrels: import each module directly from its file.
- Everything lives as close as possible to where it is used. A component's Server Action, types and children sit in its folder inside the route's `_components/` (e.g. `_components/company-form/actions.ts`). Never import a page's `_components/` from another route tree.
- `actions.ts` with `'use server'` is only for mutations called from the client. A function a Server Component calls to read data is not a Server Action: name its file `data.ts` (e.g. `src/app/(pages)/(private)/configuracoes/data.ts`).
- A page that reads the database renders on each request: a page that reads the session is dynamic on its own (`headers()`), and the others' `data.ts` call `connection()` from `next/server` (e.g. `/status` and `/configuracao-inicial`). Otherwise `next build` prerenders the data of the build.
- React Compiler is enabled (`reactCompiler: true` in `next.config.ts`).

### Database & local services

- `src/infra/compose.yml` declares two Postgres services: `database` (port `5432`, persistent volume, `.env.development`) and `database-test` (port `5433`, `tmpfs`, `.env.test`), so the tests never touch the development data.
- `pnpm dev` chains `services:up` → `services:wait:database` → `migrations:up` → `next dev`. The containers keep running after `next dev` stops: use `pnpm services:stop` or `pnpm services:down`.
- `.env.development` and `.env.test` are committed and hold only local values. They hold a local `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL`; production generates its own secret (`guias/instalacao.md`). The git-ignored `.env.local` holds the credentials of the real device (`DEVICE_IP`, `DEVICE_LOGIN`, `DEVICE_PASSWORD`, `DEVICE_SESSION_TOKEN`), used by the external tests and by `pnpm test:mocks:create`. Never put them in a committed file.
- The schema is in `src/infra/database/schema.ts` (the tables, with the database names of the columns, constraints and indexes) and the relations the queries load in `src/infra/database/relations.ts` (`defineRelations`). `drizzle.config.ts` points `drizzle-kit` at them.
- `pnpm migrations:generate <name>` diffs the schema and writes a migration (`migration.sql` and `snapshot.json`) into `src/infra/database/migrations/`; `pnpm migrations:up` applies the pending ones. Generated migrations and snapshots are not linted or hand-edited. A data change (e.g. the default justification types of the companies created before them) goes in a custom migration (`pnpm exec drizzle-kit generate --custom --name <name>`), whose SQL is written by hand.
- `src/infra/database/client.ts` creates one client per process (kept on `globalThis` outside production, so hot reload doesn't open new pools). Repositories import the tables from `schema.ts` and use `database.query.<table>` (the relational queries, with `with` for the relations) for reads, `database.insert`/`update`/`delete` with `.returning()` for writes, ``database.execute(sql`...`, 'objects')`` for raw queries and `database.transaction(async (tx) => ...)` for writes that must succeed or fail together. A transaction can't open another one, so a write that a larger transaction reuses takes an optional `tx` and runs through `runInTransaction(tx, ...)` (e.g. `scheduleRepository.save`, called by `synchronizationRepository.importFile`).
- The PIS is unique per company (`users_companyId_pis_key`), and `punch_records` references the employee by `(company_id, pis)`, so the same PIS in two companies never collides. The NSR is also unique per company, and every punch record query takes the `companyId`. The PIS is stored with 12 digits, the size the AFD reserves for it (`PIS_LENGTH`).
- The better-auth tables are `auth_users`, `auth_sessions`, `auth_accounts`, `auth_verifications`, `members` and `invitations`, mapped in the adapter's `schema` option (`src/infra/auth.ts`). Their Drizzle keys keep better-auth's field names (`organizationId`, `userId`, ...) with snake_case columns, since the adapter looks up the fields by key. `companies` is the organization table: the fields read from the device stay empty until the first import. The device credentials belong to the company (`companies.device_credentials_id`).

### Production & releases

- The app runs at the store, on a server in the same network as the time clock, from the image `ghcr.io/supermercado-baratao/easy-ponto`. The `Dockerfile` builds the `standalone` output (`output: 'standalone'` in `next.config.ts`) and serves it on port `3003` as the `node` user.
- The root `compose.yaml` is the production one (the app and Postgres, with no database port published and a `healthcheck` the app waits for), and `.env.example` is the template of its `.env`. The device credentials are not in it: they are saved in the database through `/configuracoes`. Its project name comes from the folder, and the dev compose is also named `easy-ponto`, so testing it on a development machine from a folder named `easy-ponto` takes over the development database: use another folder or `-p`.
- In production, `src/instrumentation.ts` applies the pending migrations with the `drizzle-orm` migrator (`src/infra/database/migrate.ts`) before the server takes requests. Output file tracing doesn't pick up the migrations folder, so the `Dockerfile` copies it. Outside production, `pnpm dev` and the tests run `drizzle-kit migrate` themselves.
- Without `BETTER_AUTH_SECRET`, better-auth refuses to run in production, so the `.env` of the store and the smoke test of the release set it.
- `.github/workflows/release.yml` builds the image for `linux/amd64` and `linux/arm64` on native runners, runs a smoke test against a Postgres service (`/status` reads the database, so it also checks the migrations) and, on a `vX.Y.Z` tag that matches the `package.json` version, pushes the image and creates the release. On pull requests it only builds and runs the smoke test, when the files the image depends on change.
- The install, update and backup guides for the store are in `guias/`, in Portuguese, since the people who follow them are users.

### Time clock & synchronization

- Easy Ponto is sold to companies with other time clocks, so each device model is an adapter. The contract is `TDeviceAdapter` (`src/models/device/types.ts`): `loadCompany` and `loadUsers` return the normalized company and users (`TDeviceCompany`, `TDeviceUser`, every document as a string with all its digits, the PIS with the 12 of the AFD) and `loadAfd` returns the AFD text. The AFD is the file of Portaria 671, which every REP exports, so its parsing (`synchronization/_utils/afd.ts`) is shared. The model of the device is saved with the credentials (`devices_credentials.model`, picked in `/configuracoes`), and `deviceModel.connect(credentials)` returns its adapter. The synchronization only sees the contract, and a flow that makes several calls reuses one adapter, so they share a session.
- To add a device: write the adapter in `src/models/device/adapters/<vendor>/` (the API, the raw types and the mappers to the normalized types stay there), add the model to `DEVICE_MODELS` and `DEVICE_MODEL_LABELS` (`src/models/device/utils.ts`) and register its factory in `ADAPTERS` (`src/models/device/model.ts`). Adapters are written only when a company needs them; today there is only `control-id-idclass`.
- The Control iD iDClass (`adapters/control-id/`) answers over HTTPS with a self-signed certificate and non-standard HTTP, so `createApiInstance` turns off `rejectUnauthorized` and enables `insecureHTTPParser`. Requests send `mode=671` (the AFD of Portaria 671). `getSession` reuses the session token saved in `devices_sessions` while the device accepts it, and logs in again otherwise, and `controlIdApi.loadUsers` reads the users in pages of 100. The device returns the documents as numbers, so the mappers pad them with the zeros it drops.
- The migration reports are also adapters, one per source system (`src/models/time-card-report/`). The contract is `TTimeCardReportAdapter` (`types.ts`): `read(file)` returns the normalized `TTimeCardReport` (the period, the company data, the users, the schedules, the punch records, the justifications by their code in the source system and the hours bank totals), with the employees identified by name. The adapter only reads: matching the names to the saved users and saving belong to `synchronizationModel` (`synchronization/_utils/report.ts`), so a new format gets them for free. The format is picked in the "Sistema de origem" select next to each import button (`blocks/report-format-select.tsx`, inside `blocks/report-import-form.tsx`) and the action passes it on; `timeCardReportModel.read(format, file)` validates it and calls the adapter. A layout the adapter can't read throws `InvalidExcelFileError` (`src/models/time-card-report/errors.ts`).
- To add a report format: write the adapter in `src/models/time-card-report/adapters/<system>/` (the parsing, the system's own codes and rules and their tests stay there), add the format to `TIME_CARD_REPORT_FORMATS` and `TIME_CARD_REPORT_FORMAT_LABELS` (`src/models/time-card-report/utils.ts`) and register it in `ADAPTERS` (`src/models/time-card-report/model.ts`). Today there is only `secullum`.
- `synchronizationModel` (`src/models/synchronization/model.ts`) holds the flows: `synchronizeCompany`, `synchronizeUsers` (creates the new device users, updates the saved ones by PIS and creates the employees' accounts), `synchronizeAfd` (parses the AFD and saves the records, skipping the NSRs already saved) and `importFile` (reads the migration report through its adapter, updates the users by name and the company registration, creates the punches marked with `*`, which are not in the AFD, saves the "Horário de Trabalho" block as each user's schedule and creates the justifications). The imported schedule starts on the first day of the report's period: Secullum prints the current schedule, not the one in effect during the period, so no date in the report says when it began. Everything `importFile` saves is written in a single transaction (`synchronizationRepository.importFile`).
- The justification codes of the Secullum report (`src/models/time-card-report/adapters/secullum/justification.ts`) are read from the punch cells by their column label. A code in every pair of the day's schedule is a whole day justification, and consecutive whole days with the same code become one interval. A code in some of the pairs is a shift justification with the times of that pair in the imported schedule, or a whole day when the schedule has no such pair. `Feriado` and `Falta` are skipped, and so is `Folga` (the weekly rest) on a day the imported schedule has no pair; on a workday of the schedule (a rotation of the 5x2 or the store closed) `Folga` is a code like any other, so the day isn't an absence. The match is case-sensitive: `FOLGA`, in uppercase, is a code of the store. A code resolves to the type saved for it in an earlier import (`justification_code_mappings`, by company and report format), or else to the type with the same code; otherwise `importFile` saves nothing and returns the unknown codes. The user then creates a type or picks a saved one for each code (`blocks/unknown-codes-dialog.tsx`), and the choice is saved with the import, so each code is asked once. Removing a type forgets the codes saved for it. A justification that overlaps a saved one is skipped: an identical one silently (importing the same report again), a different one counted in the result.
- `journeyModel.calculateDays` (`src/models/journey/`) computes each day (expected hours, worked hours, absence, lateness, compensation (the time of a justification that deducts from the hours bank), overtime of 60% and 100%) from Easy Ponto's punches, schedules, holidays and justifications, never from the Secullum totals. The rule values (the tolerances) are constants in `src/models/journey/utils.ts`: the journey rules are provisional until the CLT review (#65), so keep them there instead of scattering literals.
- `hoursBankModel` (`src/models/hours-bank/`) sums those days by employee for the hours report (`/relatorio-de-horas`): balance = previous + overtime 60% + overtime 100% + adjustments − absences − lateness − compensation. Closing a period saves each employee's balance (`hours_bank_balances`), which becomes the previous balance of the next period. A closed period shows the saved values instead of recalculating, the next one must start the day after it, only the last closing can be reopened, and the adjustments dated inside a closed period can't change.
- The initial hours bank balance comes from a Secullum Cartão Ponto report that starts when the bank started (balance zero): `synchronizationModel.importInitialBalance` saves the totals the Secullum adapter reads (`src/models/time-card-report/adapters/secullum/hours-bank.ts`), which takes the absences, overtime 60% and 100% and adjustments from each employee's totals, reads the totals by their column label (not by position), counts each justification code of a day (a whole workday in two pairs, half a day in one, never `Folga`) and credits a whole workday for a worked holiday, the rules of the spreadsheet the store used before the migration. `importInitialBalance` resolves those codes like `importFile` (asking for the unknown ones) and deducts the minutes of the codes whose type has the `deduct` effect, never a fixed code. They are Secullum migration rules, not Easy Ponto's journey, so they stay in the adapter instead of `src/models/journey/utils.ts`. The result is saved as a closing with `initial: true` ending on the report's last day, accepted only while the company has no closing; discarding it is reopening that closing. Employees are matched by name, and the unmatched ones are returned and skipped.
- Each company is created with the default justification types (`DEFAULT_JUSTIFICATION_TYPES` in `src/models/justification-type/utils.ts`: `COMPENSACAO`, which deducts from the hours bank, and `ABONO`, `ATESTADO`, `AUSENCIA LEGAL`, `FERIAS` and `LICENCA`, which excuse), editable and removable like any other. "Folga" is only the weekly rest of the schedule; a day deducted from the hours bank is a compensation (`compensation` in the code). The list is a product organization, not a legal one, until the CLT review (#65).
- A user's `status` (`USER_STATUSES` in `src/models/user/utils.ts`: `registered`, `probation`, `on-leave`, `dismissed`) is edited only in `/funcionarios`: `synchronizeUsers` creates new users as `registered` and never overwrites it. Vacation and compensation are justifications, not statuses. The employee list hides the inactive statuses (`INACTIVE_USER_STATUSES`, today only `dismissed`) unless the filter asks for them.
- The schedule agenda (`/expedientes`) shows each employee's schedule in effect today, with the lunch and journey of each day and the CLT alerts from `summarizeScheduleDay` (lunch above 2h, journey above 8h, more than 6h without a break). The alert limits are constants in `src/models/journey/utils.ts`, next to the tolerances, until #65. The time filter matches the first entry or the last exit of any day.
- `vacationPlanModel` (`src/models/vacation-plan/`) keeps the vacation month planned for each employee per year (`/ferias`), which lists the active employees and the inactive ones with a plan in that year. Registering the vacation creates a whole-day justification of a type the user picks (there is no fixed vacation type: the default `FERIAS` can be edited or removed) and links it to the plan. The month of a registered vacation can't change until its justification is removed (the link becomes `null`). The acquisition and concession periods wait for the CLT review (#65).
- The workload calendar (`/calendario`, `src/models/workload-calendar/`) plans the load of each day of the month: 7:20 from the 11th to the 26th and 8:00 at the start and end of the month, none on Sundays and holidays. It shows the total of each week (Sunday to Saturday) and of the month, the standard journey (worked days × 7:20) and the excess. It is only a plan: `journeyModel.calculateDays` doesn't read it. The values are constants in `src/models/journey/utils.ts` until #65.
- There is no public sign-up. `/configuracao-inicial` creates the first company and its owner while no account exists (`accountModel.setup`). Every way into the private area (the setup, the sign-in, the password change and the landing page) leads to `/registros-de-ponto`, so its `data.ts` sends an editor to `/configuracoes` while the company isn't configured (`isCompanyConfigured` in `src/models/company/utils.ts`: the device credentials saved and the company imported from the device), and `/configuracoes` says what is missing. A viewer stays on `/registros-de-ponto`, since `/configuracoes` only edits. An employee with a valid CPF gets an account when `synchronizeUsers` or `importFile` saves them (`accountModel.createEmployeeAccounts`): the email is derived from the CPF (`getEmployeeEmail`, on the reserved `.invalid` domain), so the employee signs in with the CPF, and the password is the default one (`getDefaultPassword` in `src/models/account/utils.ts`: the first five CPF digits and the last word of the name, lowercase and without accents), which must be changed on the first access (`auth_users.must_change_password`). The same CPF in another company reuses the account and its password. The admin resets an employee's password to the default one in `/funcionarios` (there is no email service). An employee (`members.role` `employee`) only reaches `/meu-ponto`, a read-only page with their punch records and the journey of each day of the chosen month, plus the month totals. Its `data.ts` takes the company from the active membership and the employee from the signed-in account (`users.auth_user_id`, `userModel.findByAuthUserId`), never from the URL, so the page reads no PIS. `/meu-ponto` and `/registros-de-ponto` compute the days through `journeyModel.findUserDays` and render the same `blocks/punch-records-table.tsx`, whose editing menu is a `renderActions` prop that only `/registros-de-ponto` passes, and only to an editor.
- The AFD records of a PIS that no saved user has are dropped on purpose, until #30 decides how to keep the history of former employees.
- Dates and times are stored as UTC wall-clock values: `@/infra/dayjs` exports `dayjs.utc`, so a punch at `07:27` is saved as `07:27Z`. Always build dates through it, and take the current date from `wallClockNow()` (the store's local time in São Paulo), never from `dayjs()`.

### Forms

- Forms are client components that call `useFormState` (new forms use `useActionState`, its current name in React 19) with a Server Action from their `actions.ts`, and render `FormCard`, `FormField` and `Select` from `src/app/components/ui/custom/form.tsx`, with `Loader` in the submit button while the action is pending (pass the button's text in `label`, so the button keeps its accessible name).
- React resets a form after its action, even when validation fails. On an error, the action returns the typed values in `values` and the form uses them as the `defaultValue` (e.g. `feriados/_components/holiday-sheet/actions.ts`). Passwords are never returned.
- A form submit wraps the model call in `handleFormAction(model.method, state, formData)` (`src/entry/form-action.ts`), which turns the `FormData` into an object, returns `data` and `success` and maps the errors: a `ZodError` becomes `errors` (the first message per field, in Portuguese through `z.config(pt())`), a `KnownError` becomes its `message` and `action` and anything else becomes `fatalError`. An action that is not a form submit (e.g. `importFromDevice`, a removal, a closing) wraps its call in `handleAction(() => ...)` (`src/entry/action.ts`), which maps the errors the same way but treats a `ZodError` as unexpected, since there is no field to show it on, and an action with errors of its own (`importFile`) hands the rest to `toActionError`. The form forwards `message` and `action` in its state, and the client shows any error through `showActionError(state)` (`src/app/utils/action-error.ts`), a toast (`sonner`) with the message and action, or the generic one for `fatalError`. Every path logs the original error with `console.error`, and only a `KnownError` sends its text to the client.
- A model throws a `KnownError` (`src/infra/errors.ts`) for what the user can resolve, with the `message` and `action` in Portuguese: `ValidationError` for a broken rule and `NotFoundError` for a record missing from the company (usually changed or removed in another tab), passing the internal detail (ids) as the `cause`. A domain's own errors extend them in its `errors.ts` (e.g. `src/models/device/errors.ts`). A plain `Error` is for what the UI never lets happen (e.g. a role the actor can't assign), which the client sees as unexpected.
- Each device adapter turns its failures into the device errors of `src/models/device/errors.ts` (wrong login or password, unreachable, too slow, unexpected response), as `control-id` does in an axios interceptor (`adapters/control-id/errors.ts`), and sets a `timeout` on its requests. `deviceModel.connect` takes the company's credentials as they are and throws `DeviceNotConfiguredError` when there are none.
- Each model validates its own input with its `schema.ts` (`schema.parse(input)`), never in the action. Always persist the data Zod validated, never the raw input.
- Whatever can be created can also be edited, and every field of a form is editable. The only exception is immutable data, such as the `id`, the timestamps and the fields read from the AFD (`nsr`, `afdDatetime`, ...).

### Linting & formatting

- ESLint uses native flat config (`eslint.config.mjs`), extending the `core-web-vitals`/`typescript` configs from `eslint-config-next`, plus `eslint-plugin-unicorn`, `eslint-plugin-simple-import-sort`, `eslint-plugin-tailwindcss`, `eslint-plugin-promise`, `eslint-plugin-prefer-arrow-functions`, `eslint-config-prettier`, and `@eslint/json`/`@eslint/markdown` for JSON/Markdown files. `eslint-plugin-tailwindcss` reads the theme from `src/app/styles/globals.css`, and its rule docs are in `node_modules/eslint-plugin-tailwindcss/docs/rules/`; classes defined in plain CSS go in the `whitelist` of `tailwindcss/no-custom-classname`.
- `@typescript-eslint/explicit-function-return-type` applies to `src/**/*.ts`, except the tests, the hooks, Route Handlers, the database client and the database schema (whose column helpers rely on Drizzle's inferred builder types).
- `unicorn/no-top-level-assignment-in-function` is off in `src/tests/**`, since tests share state set in `beforeAll` or in an earlier test through top-level `let`.
- The `pnpm peers check` warnings about ESLint 10 come from the plugins of `eslint-config-next`; `pnpm eslint:check` passes.
- `next lint` no longer exists (removed in Next.js 16). Use `pnpm eslint:check` / `pnpm eslint:fix` and `pnpm prettier:check` / `pnpm prettier:fix`.
- `pnpm type-check` runs `next typegen` first, so a clean checkout has the generated route types.
- The `review-copy` skill (`.claude/skills/review-copy/`) reviews the text in the code (naming, comments, test descriptions, UI copy, docs); use it on a diff before opening a pull request.
- Prettier style: single quotes, no semicolons, no trailing commas (`.prettierrc`). Base whitespace rules are in `.editorconfig`.

### Code comments

- Comments only record **why** a decision was made, ideally with a reference (docs link, issue number, upstream bug). Never write comments that explain what the code does or how it works.
- Default to no comment. Add one only for a non-obvious choice that someone might "fix" by mistake.
- Write comments in English.

### Git hooks (husky)

- `pre-commit`: runs `lint-staged` (`lint-staged.config.js`), which runs ESLint, Prettier and `vitest related --project unit --passWithNoTests` on the staged files, by type. Only the unit tests run there, so a commit never needs the services.
- `commit-msg`: auto-prepends the emoji prefix from the Commit Rules below based on the leading word (e.g. `feat: ...` → `✨ feat: ...`), then runs `commitlint` (`commitlint-config-emoji-convention`). Type the plain word and let the hook add the emoji.
- `pre-push`: runs `pnpm type-check`, `pnpm test:integration` and `pnpm test:e2e`.
- The `commit-msg` hook's `sed` matches `fixup!` as `fix` and produces an invalid type, so `git commit --fixup`/`--autosquash` don't work. To fix the commit you just made in the same task, use `--amend`.

### Testing

- Unit tests: **Vitest** (`vitest.config.mts`, project `unit`), `jsdom` environment. They pick up `src/**/*.test.{ts,tsx}` outside `src/tests`, next to the code they test (e.g. `src/models/synchronization/_utils/afd.test.ts`). A test that needs Node APIs (e.g. `File` with `xlsx`) starts with `// @vitest-environment node`. Test files import `describe`/`test`/`expect`/`vi` from `vitest` (no globals).
- Integration tests: project `integration`, in `src/tests/integration/`. They call the models directly against `database-test`: `pnpm test:integration` starts the services and runs the migrations on it first. `src/tests/setup.ts` loads `.env.test` before anything else, and `orchestrator.clearDatabase()` refuses to truncate a database whose name doesn't end in `_test`. The files run one at a time, since they share the database.
- External tests: project `external`, in `src/tests/external/`. They use the real device with the credentials of `.env.local`. They never run in CI or in the hooks, and `pnpm test:external` is run only when nothing else can check the change.
- E2E tests: **Playwright** (`playwright.config.ts`), in `src/tests/e2e`, with a `setup` project (`auth.setup.ts`, which signs in as the admin and saves the session to the git-ignored `playwright/.auth/`) and the `chromium` project, which depends on it and reuses that session. A test without a session uses `SIGNED_OUT_STORAGE_STATE` (`src/tests/_utils/e2e-auth.ts`). The config loads `.env.test`, and the `webServer` runs `pnpm test:services` and then `next dev` on port `3001` with `NEXT_DIST_DIR=.next/e2e` (read by `distDir` in `next.config.ts`), so it uses `database-test` and runs next to a `pnpm dev` already open (`next dev` locks its output folder). Outside CI it reuses a server already on port `3001`. Next adds the `.next/e2e` type globs to the `include` of `tsconfig.json`, so keep those entries committed. Assertions wait up to 15s (`expect.timeout`), since `next dev` compiles each route on its first request.
- `src/tests/e2e/global-setup.ts` clears `database-test` and populates it with the mocked data before the E2E tests, including the admin account of `MOCKED_ADMIN` (`src/tests/orchestrator.ts`); `orchestrator.findMockedCompanyId` returns its company. A test that needs other users or companies creates them in a company of its own, so the mocked employee list stays as the other tests expect it. The integration and E2E tests share `database-test`: never run them at the same time.
- `src/tests/_mocks/` holds fake device data (`afd.txt`, `device-users.ts` with the normalized users, `parsed-afd.ts`), generated from the real Control iD by `pnpm test:mocks:create`, which replaces every PIS and name with Faker values. Real employee data (names, PIS, CPF) never goes into the repository, an issue or a pull request.
- `src/tests/orchestrator.ts` centralizes the setup: `waitForAllServices`, `clearDatabase`, `populateDatabaseWithMockedData`, `populateDatabaseWithRealData` (external tests only) and `createMember` (an account with a given role in a company that signs in without changing the password, including an employee, which `memberModel` never adds). `src/tests/_utils/` holds helpers used only by tests, such as `mockDeviceAdapter`, which replaces the adapter `deviceModel.connect` returns, so a test never reaches a device.
- Only test logic we wrote (the models' rules, the AFD and spreadsheet parsing, mappings, the queries). Don't test library or framework behavior. Older issues may ask for tests that break this rule: skip them and list them as dropped in the closing comment.
- Assertions check real behavior, not the incidental state of the fixture.
- CI (`.github/workflows/ci.yml`, on `pull_request`) runs, in order: `commitlint` over the PR's commit range, `pnpm type-check`, `pnpm eslint:check`, `pnpm prettier:check`, `pnpm test`, `pnpm test:integration`, then installs Chromium and runs `pnpm test:e2e`.

- Tailwind CSS v4 (`@tailwindcss/postcss`). Global styles live in `src/app/styles/globals.css`, which imports `tw-animate-css` and the shadcn base stylesheet (`shadcn/tailwind.css`). The fonts are Geist and Geist Mono (`next/font/google`).

The sidebar items render a `Link` through the `render` prop of `SidebarMenuButton`, and a `Button` rendered as another element takes `nativeButton={false}`. ## Development Workflow

The end-to-end flow (planning, issues, branches, commits, pull requests and closing) is described in [`docs/development-workflow.md`](./docs/development-workflow.md). Follow it for any issue.

## Branch Rules

Work for an issue is committed on a new branch, never directly on `main`. Branch names follow `<scope>/<title>#<issue>`, or `<scope>(<target>)/<title>#<issue>` when the work is very specific:

- `<scope>` is one of the semantic prefixes from the Commit Rules below, without the emoji (`feat`, `fix`, `docs`, `chore`, ...).
- `(<target>)` is optional: the page, component or other specific area the work touches (e.g. `settings`).
- `<title>` is a short, lowercase, hyphen-separated summary in English.
- `#<issue>` is the number of the associated issue.

Examples: `feat/punch-records-page#12`, `fix(settings)/company-state#11`. Parentheses and `#` are special characters in shells, so quote the branch name in commands (e.g. `git switch -c 'fix(settings)/company-state#11'`).

## Issue Rules

Before closing an issue, tick every completed checklist item (`- [x]`) in its body, e.g. with `gh issue edit <number> --body-file <file>`. Don't close an issue that still has unchecked items unless they were dropped or moved, and say so in the closing comment.

## Documentation Rules

`AGENTS.md` and `README.md` record only project conventions: what to do, where things live and how to handle a given case. Answers to the user's one-off questions stay in the conversation and are not written into them. Keep a "why" only when it prevents a likely mistaken "fix". If a change touches a convention, update both files in the same branch.

## Task Rules

Never start working on a task on your own, even when asked to move on to the next one or in auto/agentic mode. First present a summary of the plan (the issue, branch name, steps, files touched and any open decisions) and wait for explicit approval before creating the branch, installing dependencies or editing code. Read-only investigation (issues, docs, code) needs no approval.

## Commit Rules

Never run `git commit` on your own, even in auto/agentic mode. Only propose a commit message when the user asks for one, and create the commit only after explicit approval of that message.

Commit messages must be in English and follow this format:

- Use the following semantic prefixes: `🎉 init, ✨ feat, 🐛 fix, 📚 docs, 💎 style, 📦 refactor, 🚀 perf, 🚨 test, 🛠 build, ⚙️ ci, ♻️ chore, 🗑 revert`
- The message must be in the imperative mood and in lowercase.
- Write the commit body.
- Reference an associated issue by number, if it exists, using the format `Issue: #<number>`.

Example:

```text
✨ feat: add punch records page

List the punch records of the selected employee with the following features:
- Filter by period
- Show the records added by hand

Issue: #12
```
